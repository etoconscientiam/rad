# RAKURS Router — какой скилл запускать

Сверяйся в начале задачи, потом вызывай выбранное. Порядок: сперва правила **always**,
потом строка таблицы, потом цепочка **после изменений**. Конкретное правило бьёт общее.

## Always (любая задача в проекте)
1. Соблюдать `AGENTS.md` и `CLAUDE.md` в корне: `_source/**` только на чтение, секреты не печатать,
   git-операции только по просьбе, первичный сигнал = поведение, видимое пользователю.
2. Требования — `docs/04-repo-review.md` (стек и этапы), предметная модель — `docs/02-domain-model.md`.
   Дизайн-референс — только `_source/prototype/`.
3. Новая выгрузка дизайна из Claude Design — тянуть инструментом **DesignSync**
   (deferred, грузить через ToolSearch), не WebFetch и не браузером.
4. Деньги: любой расчёт цены на клиенте обязан иметь серверную проверку. Правка формул — только после сверки с заказчиком.
5. Самое малое связное изменение на владеющем слое.

## Маршрут по типу задачи
| Задача… | Запускать |
|---|---|
| Обдумать идею, взвесить варианты, «не знаю с чего начать» | `dale-brainstorm` |
| Спроектировать фичу / написать план-документ | `planning:design`, затем `planning:implement` |
| Многошаговая работа, которую стоит разметить до начала (≥3 связанных шага) | `dale-graph` |
| Довести одну задачу до проверенного «готово» (действие → проверка → правка) | `dale-loop` |
| Рискованное: миграция схемы, платежи, рефактор конфигуратора, прод | `dale-max` (адверсариальный ревьюер-гейт) |
| «Проверь / точно ли работает / подтверди» | `dale-proof` |
| «Покажи / визуализируй / сравни наглядно» | `dale-visualize` (перед цветом читать `dataviz`) |
| Макет экрана до вёрстки | `mockuplm:mockup` |
| Схема БД (заказы, позиции, статусы) | `datamodellm:datamodel` |
| Архитектурная схема, диаграмма потока | `excalidraw:excalidraw` |
| Что-то с Claude/Anthropic API, модели, цены | сперва читать `claude-api` |
| Регулярный/по расписанию запуск | встроенные `/loop` или `/schedule` |
| Коммит (только когда просят) | `developer:git-commit` |

## После нетривиального изменения кода (цепочка)
1. `run` / встроенная проверка — прогнать затронутый сценарий в браузере.
2. `dale-proof` — превратить «работает» в вердикт PROVEN/PARTIAL с указанием границ.
3. `code-review` — корректность и чистка перед коммитом.
4. `security-review` — если трогали оплату, авторизацию, приём заказа или переменные окружения.

## Чего НЕ запускать в этом проекте
- `design-spellbook` — дизайн-язык уже зафиксирован бренд-спекой «Каркас». Скилл толкает к «необычному и яркому»,
  это прямо противоречит индустриальному минимализму и правилу одного красного акцента.
- `naming-spellbook` — бренд уже назван (Ракурс / RAKURS / რაკურსი), логотипа по спеке нет.
- `affiliate-site-builder`, `seo-content-discipline` — заточены под affiliate/обзорные сайты
  лицензированных операторов и под обход AI-детекторов. Здесь мастерская с собственным тоном голоса.
- `funnel-*` (build, build-clone, parse-donor, deploy, verify) — про клонирование квиз-воронок с донора.
  К екому с конфигуратором отношения не имеют.
- `web-dev-foundations` целиком — он про статические сайты без сборки (.htaccess, zip-поставка, PROJECT_STATE.md).
  Стек здесь Next.js. Брать из него только дисциплину CHANGELOG и мобильные защитные паттерны — вручную, не как скилл.

## Не переусердствовать
Однострочная правка, справка или просто разговор — делать сразу, без скиллов.
